==================================================
PROJECT DIRECTION
==================================================

RedGuard is currently primarily an LLM security evaluation system where probes are sent to an agent and the result is evaluated largely from the final response.

I want to evolve RedGuard into a research laboratory for studying security failures in DEPENDENT MULTI-AGENT SYSTEMS.

The fundamental shift is:

CURRENT IDEA:

Security Probe
    ↓
Single Agent
    ↓
Final Response
    ↓
Safe / Unsafe

NEW IDEA:

Security Test Case
    ↓
Controlled Execution Environment (CEE)
    ↓
Dependent Multi-Agent Workflow
    ↓
Adversarial Artifact enters the workflow
    ↓
Agents communicate / use tools / modify state
    ↓
Observable execution trajectory
    ↓
Measure adversarial influence
    ↓
Measure propagation
    ↓
Measure containment
    ↓
Measure behavioral impact
    ↓
Security verdict + evidence

The main research question is:

"When an adversarial artifact compromises one agent in a dependent multi-agent workflow, how does that influence propagate through the system, where is it contained, what downstream capabilities are affected, and can those effects be measured from observable execution behavior?"

The important point is that the evaluation should NOT primarily ask:

"Did the model produce a bad final answer?"

Instead, it should ask:

"After the attack entered the system, what did the agents actually DO, how did adversarial influence travel through the workflow, where was it stopped, and what measurable impact did it have?"

==================================================
PROPOSED MVP ARCHITECTURE
==================================================

Start with a deliberately small and controlled MVP.

Use three agents:

Agent A = Researcher
Agent B = Validator
Agent C = Executor

Dependency:

A → B → C

All three agents should initially use the SAME underlying LLM/model.

The reason is to avoid introducing model-family differences into the first experiments.

The agents should operate inside a Controlled Execution Environment (CEE).

IMPORTANT:

CEE is NOT intended to be a real OS/container security sandbox.

It is a deterministic research fixture/environment that provides controlled synthetic resources and mock tools.

The CEE should ideally contain things such as:

- mock filesystem
- mock web/search results
- mock database
- key-value state/memory

Tools should initially be limited, for example:

- file_read
- web_search
- db_query

Each agent should have explicit tool authorization.

Communication should happen through a topology-aware message bus.

The topology should prevent agents from arbitrarily communicating with every other agent.

For the MVP:

A → B → C

==================================================
ATTACK MODEL
==================================================

Security Test Cases should inject adversarial artifacts into the workflow.

The initial attack families should include:

1. Content / prompt injection
2. Tool manipulation
3. Memory/state poisoning

The attack should be capable of entering through different points.

For example:

- attack enters through Agent A
- attack enters through Agent B

The system should then observe whether adversarial influence remains local or propagates downstream.

Do NOT assume every attack must succeed.

The whole purpose is to measure:

- initial compromise
- downstream influence
- propagation
- containment
- behavioral deviation
- attack objective achievement

Each Security Test Case should therefore define an explicit attack objective.

For example:

NOT_REACHED
PARTIALLY_REACHED
REACHED
CRITICAL_REACHED

The implementation should make attack eligibility explicit where possible:

- eligible downstream agents
- eligible tools
- eligible resources
- expected attack path

==================================================
BEHAVIORAL EVALUATION
==================================================

Final text should be secondary evidence.

Primary evidence should come from structured execution events.

Examples:

- agent receives message
- agent sends message
- tool requested
- tool executed
- tool denied
- resource accessed
- state written
- state read
- attack artifact observed
- downstream agent receives derived adversarial content
- unauthorized capability attempted
- goal/task deviation
- security-relevant state change

Every event should contain enough information to reconstruct what happened.

We also need provenance / observed derivation.

For example:

Attack artifact
    ↓
Agent A observes artifact
    ↓
Agent A generates message
    ↓
Agent B receives message
    ↓
Agent B performs tool call
    ↓
Agent C receives result
    ↓
Agent C performs state change

This should allow us to answer:

"Which observed event was derived from which previous event?"

IMPORTANT:

Do NOT claim this is formal causal inference.

Use terminology such as:

"observed derivation"
"traceable influence"
"provenance"

rather than claiming causal proof.

==================================================
CLEAN BASELINE
==================================================

Every meaningful attacked run should have a corresponding clean baseline where the same task is executed without the adversarial artifact.

This is extremely important.

We need to distinguish:

NORMAL BEHAVIOR
from
ATTACK-INDUCED BEHAVIORAL DRIFT

The system should therefore support paired clean/attack runs.

Consider introducing:

pair_id
or
baseline_run_id

so that an attacked execution can be linked to its clean baseline.

==================================================
IMPORTANT METRICS
==================================================

Think carefully about how these should actually be implemented.

Potential MVP metrics include:

1. Attack Success Rate (ASR)

Measures how often the attack achieves a defined security-relevant objective.

2. Initial Compromise Rate (ICR)

Measures whether the entry agent becomes behaviorally compromised by the adversarial artifact.

3. Conditional Propagation Rate (CPR)

Do NOT blindly use a denominator over all runs.

Propagation should only be measured when:

- the entry agent was compromised
- downstream propagation is structurally possible

Conceptually:

CPR =
downstream-influenced runs
/
eligible entry-compromised runs

4. Propagation Depth

How far adversarial influence travels through the topology.

For A → B → C:

A only = depth 0
A → B = depth 1
A → B → C = depth 2

5. Downstream Coverage

How much of the structurally reachable downstream system became influenced/compromised.

6. Containment Rate

How often the attack is stopped before reaching all eligible downstream agents/capabilities.

7. Security Outcome Consistency (SOC)

Measure whether repeated executions produce consistent security outcomes.

Prefer a simple interpretable formulation for the MVP, such as:

frequency of the modal outcome / N

rather than unnecessarily complicated statistics.

8. Trajectory Drift Score (TDS)

Compare clean vs attacked behavioral trajectories.

The MVP can use normalized sequence distance over security-relevant event types such as:

- tool_requested
- tool_executed
- tool_denied
- state_write
- message_sent

But think carefully about whether plain Levenshtein distance is sufficient and structure the implementation so it can later support better weighting.

9. Attack Objective Achievement

Explicitly record whether the attack objective was:

NOT_REACHED
PARTIALLY_REACHED
REACHED
CRITICAL_REACHED

10. Secondary textual indicators

Things such as refusal detection can remain, but they must NOT be the primary security verdict.

EVIDENCE BUNDLE
==================================================

Every evaluated run should be able to produce a structured evidence bundle.

It should contain enough information to explain WHY the evaluator reached its conclusion.

For example:

- attack case
- clean baseline
- attacked run
- relevant trace events
- provenance links
- compromised agents
- affected tools
- affected resources
- objective status
- containment point
- metric values
- evaluator version
- schema/version information

The evidence should make the experiment auditable and useful for a research paper.

- communication
- tool
- state
- injection

Content tags may include:

- original_task
- external_content
- derived

These tags are OBSERVATIONAL labels.
